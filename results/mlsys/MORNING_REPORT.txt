10. FOLLOW-UP, 2026-10-08: THE CUDA ASSERT, DIAGNOSED AND FIXED
--------------------------------------------------------------------------------
The gate failure in 3c was undiagnosed when this report was first written. It
is now diagnosed, reproduced on a 1x A100, and fixed. Nothing in this section
was inferred: every number is from the staged data or from a run on the pod.

ROOT CAUSE
  The gate's prompt came from data/processed/pg19_docs/documents.json, whose
  own metadata records  "tokenizer": "meta-llama/Llama-3.1-8B"  (vocab 128256).
  `load_pg19_window` returns those ids VERBATIM (gate, ~line 71) and
  `run_candidate` feeds them straight to whichever model the candidate names.
  Candidate `B_llama2_yarn8_32k_correct` is Llama-2-7B (vocab_size 32000), so
  its embedding was asked to look up ids that do not exist in it.

  Measured on the staged pool: 5,263,360 tokens across 10 books, max id 127889,
  and 458,919 of them (8.7%) are >= 32000. For that candidate's own window:
  2391 of 31744 prompt ids (7.5%), first at index 3 with value 40132, max
  127146.

  The failing op, named by CUDA_LAUNCH_BLOCKING=1 (exit only after the fact):

    transformers/models/llama/modeling_llama.py:891
        inputs_embeds = self.embed_tokens(input_ids)
      -> torch/nn/sparse.py:190  F.embedding(...)
        -> Indexing.cu:1308  indexSelectLargeIndex:
             Assertion `srcIndex < srcSelectDimSize` failed.

  On the 8x it surfaced at `torch.cuda.empty_cache()` in run_candidate's
  `finally`, because a device-side assert is reported at the next synchronising
  call. An exception raised from `finally` bypasses the handlers above it, so
  it killed the list comprehension in main() and the stage wrote NO CSV. That
  is why the incident had no rows to diagnose.

  Identity of the victim, from the manifest log: six 4-shard loads
  (Llama-3.1-8B, candidates 1-6, all completed) then one 2-shard load
  (Llama-2-7B) -- the FIRST Llama-2 candidate, exactly where a vocab mismatch
  must first bite.

  This was NOT a memory failure: peak at the abort was 13.75 GB of 40 GB.

THE OTHER THREE QUESTIONS
  (a) tokenizer / input_ids reuse across vocab sizes -- YES, for input_ids.
      `scripts/mlsys_coherence_gate.py:687-697` caches one tokenizer PER MODEL,
      so the tokenizer object is not shared. But `load_pg19_window` never uses
      it to tokenize: it returns the pool's ids. The tokenizer is only consulted
      for the BOS, for `decode`, and for the eos id set. So the ids ARE shared
      across candidates with different vocab sizes.
      The runs behave differently and are not affected the same way:
      `run_experiment._build_pg19_document_prompt` (run_experiment.py:337-345)
      goes through `_exact_token_window` (run_experiment.py:232-260), which does
      `decode` then `encode` with the TARGET's tokenizer, so the arms get
      in-range ids. Every approved campaign stage targets Llama-3.1-8B, whose
      tokenizer IS the pool's, so those stages are correct. The mismatch is
      confined to the gate's two Llama-2 controls.

  (b) a sampling call that can receive non-finite probabilities -- YES, two,
      and they are a latent device-side assert rather than a bad number:
        src/models/rasd_inference.py:322  torch.multinomial(probs, ...)
        src/models/rasd_inference.py:2039 torch.multinomial(resid, ...)
      both fed by `F.softmax` on target/draft logits (lines 317-322, 351-352,
      2035-2039). `torch.multinomial` aborts the CUDA context when the

Q1 -- KV CACHE DTYPE PER STAGE, and how many bytes per token
--------------------------------------------------------------------------------
The two flags are DIFFERENT THINGS and reading one as the other is the trap here:
`quantize_draft` / `quantize_target` are MODEL WEIGHT quantisation (4-bit NF4 via
bitsandbytes, rasd_inference.py:212-213), while `kv_quant` is the KV CACHE
(rasd_inference.py:270-271, "M4 C11 -- NF4 KV-cache"). NB4 weights do NOT imply an
NF4 cache nor the reverse.

  stage                     kv_quant  KV dtype actually used   line
  coherence_gate            n/a       bfloat16                  mlsys_coherence_gate.py:634
  engine_cap_smoke  NF4 rows true     nf4                        mlsys_engine_cap_smoke.yml:25
  engine_cap_smoke  bf16 rows false   bfloat16                   mlsys_engine_cap_smoke.yml:90,98
  natural_f1_128k           true      nf4                        mlsys_natural_f1_128k.yml:36
  natural_spec_gated_256k   true      nf4                        mlsys_natural_gated.yml:41
  vllm_ladder               n/a       bfloat16                   mlsys_vllm_baseline.py:1076

The gate does not quantise anything: `AutoModelForCausalLM.from_pretrained(...,
torch_dtype=bfloat16)` with NO BitsAndBytesConfig (mlsys_coherence_gate.py:634-628)
and generation through `model.generate` (line 515), so HuggingFace builds its own
bf16 DynamicCache. vLLM is bf16 too: the stage pins `--quantizations bfloat16` and
vLLM 0.6.3 has no NF4 KV path at all (stated in the manifest's own header for
impl_validation, mlsys_manifest.sh:1236-1243).

CONFIRMED for the memcheck config: yes, it used NF4 KV. It declares `kv_quant:
true`, `quantize_draft: true`, `quantize_target: true` and is otherwise identical
to natural_f1_128k except context (32k) and cap (128). And the pod's token
sidecars agree, because the dtype is MEASURED, not assumed: 23 of 25 sidecars
record `kv_dtype: nf4` and exactly 2 record `bfloat16` (the CAPS_prefix64_bf16
pair).

IS NF4 APPLIED TO BOTH THE TARGET AND THE DRAFT KV? NO -- TARGET ONLY.
`_make_initial_cache` (rasd_inference.py:2259-2289) is what builds the NF4 cache,
and every call site belongs to the target: generate() at :1553 and the
teacher-forced probe's two shapes at :2378 and :2391. The draft's cache is
HuggingFace's own: :1654 calls `self.draft_model(draft_ids, use_cache=True)` with
NO `past_key_values`, and later steps pass back whatever HF returned (:1894,
:2127). So the draft KV stays bf16 in every configuration -- an NF4 target with a
bf16 draft is the composition every stage runs.

BYTES PER TOKEN (Llama-3.1-8B: 32 layers x 8 KV heads x 128 head-dim = 32,768
elements per K per token, x2 for K and V = 65,536 elements/token):
  bf16                     2.0 B/elem  -> 131,072 B = 128 KiB/token
  NF4, block_size 32       0.5 B/elem codes (uint8, 2 codes/byte)
                         + 0.125 B/elem for the fp32 absmax scale (4/32)
                           = 0.625 B/elem -> 40,960 B =  40 KiB/token
NF4 is therefore 31.25% of bf16 -- 3.2x smaller. At 128k that is 16 GiB vs 5 GiB
per rank. `kv_block_size_nf4` defaults to 32 and NO campaign config overrides it
(checked: zero matches in configs/*.yml), so 40 KiB/token is the real figure; at
the bitsandbytes-standard 64 it would be 36 KiB. One-off extra: rank 0 keeps
`kv_outlier_prefix_size=128` tokens in bf16 (+16 MiB). The draft adds a bf16 cache
of its own: Llama-3.2-1B, 16 layers x 8 KV heads x 64 head-dim x2 = 16,384
elements/token x 2 B = 32 KiB/token. Drawn from the published model configs; not
re-measured on the pod.

WHAT THE CAP-SMOKE bf16 ROWS COMPARED AGAINST: their own partner, not the NF4
rows. The pairing key is (doc_id, context_length, max_new_tokens, MEASURED
kv_dtype) -- mlsys_cap_smoke_check.py:355-359 -- and the key deliberately includes
the measured precision "without it, two pairs that differ only in kv_quant land on
the same key" (:337-344). So CAPS_prefix64_bf16 is compared with
CAPS_prefix64_bf16_targetonly, and the NF4 pairs with themselves. There is no
NF4-versus-bf16 GATE anywhere; that contrast is report-only.

Q4 -- PLAINLY: yes, the 0.85-0.97 acceptance is a GREEDY REPETITION ARTEFACT
--------------------------------------------------------------------------------
The two facts coincide window by window: acceptance reaches 1.000 in exactly the
windows where tokens-in-repeat reaches 1.00, and the first window -- the only one
with real novel text -- is the only one with low acceptance (0.34-0.84). Once the
target enters a periodic cycle, the draft (same family, same context) predicts the
cycle trivially and the target accepts everything. The acceptance number is
measuring the loop, not the speculation mechanism.

WOULD THE 16 STRUCTURAL ASSERTIONS HAVE CAUGHT IT? NO, for two independent reasons.
  1. They do not test repetition at all. mlsys_cap_smoke_check.py contains ZERO
     matches for repeat/blank/share/degenerate except the word "blank" inside a
     dtype comment (:69). The natural rungs are not checked by that file anyway:
     validate_and_report -> report_spec_stage runs scripts/mlsys_losslessness.py,
     which also has no repetition test. So no stage in this campaign gates
     repetition.
  2. Where the rule DOES exist it is structurally blind to this failure. In
     mlsys_coherence_gate.verdict the repeat/blank criterion is purely RELATIVE --
     GEN_SHARE_TOLERANCE = 2.0 (line 70), candidate share vs its PAIRED BASELINE's
     share (`_share_reason`, :791-817) -- and the only ABSOLUTE ceiling is on blank
     lines (CATASTROPHIC_BLANK_SHARE = 0.90, :74). There is no absolute ceiling on
     repetition. Measured on the actual pairs:
        train_115   spec 0.9699 vs target-only 0.9043 -> 1.07x   PASS
        train_0     spec 0.6547 vs target-only 0.3627 -> 1.80x   PASS (just under)
        CAPS_prefix1024 spec 0.9245 vs target-only 0.7012 -> 1.32x PASS
     A greedy loop repeats in BOTH arms, so the ratio stays near 1 and the rule
     cannot fire. Blank shares are 0.00, nowhere near 0.90. The docstring explains
     the relative design as deliberate -- "a quantity whose absolute value ... is
     not a property of the model" -- and that reasoning is exactly what makes it
     blind here: the repetition IS a property of the run.

## STEP 1a — HOW THE DRAFT SEES THE CONTEXT (full context, or a window?)

A WINDOW, and it is applied in exactly one place. From src/models/rasd_inference.py:

    def _draft_window(input_ids, window: int):
        """The sequence the DRAFT is conditioned on: leading BOS + most recent tokens.
        ...
        """
        if window <= 0 or input_ids.shape[1] <= window:
            return input_ids
        keep = window - 1
        if keep <= 0:
            return input_ids[:, :1]
        return torch.cat([input_ids[:, :1], input_ids[:, -keep:]], dim=1)

applied in generate() as:

    draft_ids = _draft_window(raw_draft_ids, self.draft_max_len)

and `self.draft_max_len` is set once, in the model setup:

    self.draft_max_len = getattr(self.draft_model.config, "max_position_embeddings",
                         getattr(self.draft_model.config, "n_positions", 4096))
    if cfg.draft_window_cap is not None:
        cap = int(cfg.draft_window_cap)
        native = self.draft_max_len
        self.draft_max_len = min(native, cap)

So the draft sees the leading BOS plus the most recent `draft_max_len - 1`
tokens, never the full context.

CAN Llama-3.2-1B WORK AT 1M? Its native window is 131,072, so a full-context
draft cannot. It does not have to: the window is truncated to `min(native, cap)`
BEFORE the draft ever sees it, so at 1M the draft is conditioned on the last
131,072 tokens (or fewer) and never runs past its own rotary range. Two
consequences worth stating:

  * CORRECTNESS: fine at 1M with any cap <= 131,072. There is no extrapolation.
  * COST: an uncapped window means a 131k-token draft prefill and a bf16 draft KV
    of 131,072 x 32 KiB = 4.0 GiB PER RANK, replicated on all 8 (see 1c).
    `draft_window_cap: 4096` cuts that to 128 MiB/rank and makes the draft
    prefill ~1/32 the work. The 1M cells must set it.

WHAT A WINDOWED DRAFT REQUIRES: (i) the window applied in one place — already
true, and `generate_text`'s second, differently-directed truncation was removed
for this reason; (ii) the draft KV built over the window only — true, the draft
prefill runs over `draft_ids`; (iii) remembering that the draft KV then GROWS by
the generated tokens during decode (4096 + 128 = 4224 at a 128-token
generation), i.e. the draft is windowed at prefill and not re-windowed during
the generation. That is harmless at 128 tokens and would need attention only for
generations of the same order as the window.

### FINDING 3 — MY ROUND-TRIP CHECK HAD A FALSE-POSITIVE BUG, AND IT WAS GATED

  `decode()` defaults to `clean_up_tokenization_spaces=True`, which rewrites
  punctuation spacing; re-encoding the CLEANED text re-segments it, so the check
  reported "the pool was built with a different tokenizer" for pools that were
  tokenized perfectly. Measured on data/processed/pg19_1m:

    doc              cleanup=True   cleanup=False
    pg19_train_0         1.0000        1.0000
    pg19_train_1         0.0127        1.0000     <- false positive
    pg19_train_915       1.0000        1.0000
    pg19_train_1726      0.0786        1.0000     <- false positive
    pg19_train_2204      0.7316        1.0000     <- false positive
    pg19_train_2768      0.0361        1.0000     <- false positive

  All six round-trip at 100.0% once cleanup is off. The Bible matched either way,
  which is why a positive control built from ONE document missed it: the bug is
  only visible on punctuation-heavy text. Fixed in src/analysis/pool_tokenizer.py,
  and the test that would have caught it now runs over all six documents
  (tests/test_mlsys_pool_tokenizer_and_margins.py).

  This mattered more than a noisy statistic: the same check is wired into the
  coherence gate's verdict, so as written it would have FAILED legitimate rows

  no detector.

## STEP 2b — NEAR-TIE TEST, CLOSED (3rd pod, with the sidecar schema fixed)

The re-run produced real top-k logits, so the cross margin — how each arm scored the
OTHER arm's token at the divergence — is now measured rather than argued. The answer
is that the two arms pick the SAME candidates and order them differently:

  doc pg19_train_1, divergence at token 4   (own gaps: spec 0.3125, target 0.125)
    spec arm top-3:  617 (14.062)  7236 (13.750)  656 (13.688)     spread 0.375
    target arm top-3: 656 (14.062) 7236 (13.938)  617 (13.875)     spread 0.188
    -> the same THREE tokens at the top of both arms, reordered. Each arm's choice
       is the other arm's rank-3. A 0.1875-logit spread is three fp4 quantisation
       steps (logits are quantised in 0.0625). CROSS margins: 0.375 / 0.1875.

  doc pg19_train_0, divergence at token 16  (own gaps: spec 1.125, target 0.25)
    spec arm top-2:  2030 (25.250)  1789 (24.125)                  spread 1.125
    target arm top-2: 1789 (23.500) 2030 (23.250)                  spread 0.250
    -> the same TWO tokens, and the TARGET is nearly indifferent (0.25). Each arm's
       choice is the other arm's rank-2. CROSS margins: 1.125 / 0.25.
       Note the overall level: the spec arm's logits for these tokens sit ~1.5
       higher, so the shapes differ by a small scale as well as an order.

BASE RATES, which are what make this a near-tie rather than a story about one row:
at these two documents 21.9%/11.7% (train_0) and 31.2%/36.7% (train_1) of positions
have their own top1-top2 gap below 1.125. A divergence at a position with a
0.188-1.125 separation is therefore an ordinary event in this pipeline, not an
outlier, and it happens where the arms agree on the candidate SET.

VERDICT: NOT AN ENGINE BUG. The speculative and target-only arms are the same target
in two forward shapes (a gamma=4 batched verify versus single-token decode) under NF4
weights, and they diverge only where the target is numerically indifferent. This is
exactly what the project's own tie rule (TIE_GAP = 0.1) was built for, and it is why
the campaign's losslessness stage reported MISMATCH at tokens 2-16 rather than a
token-identity failure: bit-exactness is not available when the target itself is
indifferent, and the divergence costs 1-2 acceptance positions out of 128.
The honest caveat: 1.125 is the LARGEST observed margin and is above pure bf16
reduction noise, so it is recorded as "near-tie at the fp4 noise scale, largest
observed 1.125", not as "fully explained". What is established is that no logic
defect is demonstrated and the diverging positions are not unusual.

THE 128k ARM OF THE QUALITY CHECK SCORES THE SAME TOKENS, which needed data, not
code. The engine builds a prompt as the FIRST `context - gen - 1` tokens of a
document, so a 128k prompt from the same .dat would have scored a completely
different passage. `data/processed/pg19_1m_128kwin/` therefore holds, per book, the
slice `ids[917504 : 1048576]` (start = 1,047,551 - 130,047), which puts the 128k
prompt's end exactly where the 1M continuation begins. The build asserts
`array_equal` between the 1M arm's continuation ids and the 128k slice's for all six
documents, and records that in the pool metadata. Without that assertion the two ppl
numbers would not be measuring the same targets, and the comparison would be
between two passages rather than two contexts.

COST DISCIPLINE. Dead-man timer length is derived from the RATE rather than fixed,
because the operator's rule is <= $200 for this session and a fixed 9 hours is
$200.9 on the 80GB node and $287 on an H100: 510 min at $22.32/hr (=$190) on the
80GB type, 360 min at $31.92/hr (=$192) on the H100. Per-group timeouts sum to 5.3 h
of work, so the clock and the group timeouts both sit inside the cap and the timer
is a backstop rather than the mechanism. The 8x-40GB type IS in the
preference list as a fallback, and the memory arithmetic is what decides: at 1M the
per-rank projection is ~27 GB against 40 GB, and the ring is what makes that true (a
single rank would need the whole 1M KV, 41.6 GB, plus a working set that scales with
the FULL sequence). At 512k the same projection is ~14 GB/rank, comfortably inside a
40 GB card. So the 40GB node is a legitimate rung runner, and it is cheaper ($15.92/hr
vs $22.32). What NO single-GPU node can do is the 1M rung at all, whatever its size:
at world_size 1 the KV alone is 41.6 GB of NF4 and the activations scale with the
full 1,048,576 positions, so long context here is a multi-GPU property and not a
budget choice.
