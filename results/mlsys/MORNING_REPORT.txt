10. FOLLOW-UP, 2026-10-08: THE CUDA ASSERT, DIAGNOSED AND FIXED
--------------------------------------------------------------------------------
The gate failure in 3c was undiagnosed when this report was first written. It
is now diagnosed, reproduced on a 1x A100, and fixed. Nothing in this section
was inferred: every number is from the staged data or from a run on the pod.

ROOT CAUSE
  The gate's prompt came from data/processed/pg19_docs/documents.json, whose
  own metadata records  "tokenizer": "meta-llama/Llama-3.1-8B"  (vocab 128256).
  `load_pg19_window` returns those ids VERBATIM (gate, ~line 71) and
  `run_candidate` feeds them straight to whichever model the candidate names.
  Candidate `B_llama2_yarn8_32k_correct` is Llama-2-7B (vocab_size 32000), so
  its embedding was asked to look up ids that do not exist in it.

  Measured on the staged pool: 5,263,360 tokens across 10 books, max id 127889,
  and 458,919 of them (8.7%) are >= 32000. For that candidate's own window:
  2391 of 31744 prompt ids (7.5%), first at index 3 with value 40132, max
  127146.

  The failing op, named by CUDA_LAUNCH_BLOCKING=1 (exit only after the fact):

    transformers/models/llama/modeling_llama.py:891
        inputs_embeds = self.embed_tokens(input_ids)
      -> torch/nn/sparse.py:190  F.embedding(...)
        -> Indexing.cu:1308  indexSelectLargeIndex:
             Assertion `srcIndex < srcSelectDimSize` failed.

  On the 8x it surfaced at `torch.cuda.empty_cache()` in run_candidate's
  `finally`, because a device-side assert is reported at the next synchronising
  call. An exception raised from `finally` bypasses the handlers above it, so
  it killed the list comprehension in main() and the stage wrote NO CSV. That
  is why the incident had no rows to diagnose.

  Identity of the victim, from the manifest log: six 4-shard loads
  (Llama-3.1-8B, candidates 1-6, all completed) then one 2-shard load
  (Llama-2-7B) -- the FIRST Llama-2 candidate, exactly where a vocab mismatch
  must first bite.

  This was NOT a memory failure: peak at the abort was 13.75 GB of 40 GB.

THE OTHER THREE QUESTIONS
  (a) tokenizer / input_ids reuse across vocab sizes -- YES, for input_ids.
      `scripts/mlsys_coherence_gate.py:687-697` caches one tokenizer PER MODEL,
      so the tokenizer object is not shared. But `load_pg19_window` never uses
      it to tokenize: it returns the pool's ids. The tokenizer is only consulted
      for the BOS, for `decode`, and for the eos id set. So the ids ARE shared
      across candidates with different vocab sizes.
      The runs behave differently and are not affected the same way:
      `run_experiment._build_pg19_document_prompt` (run_experiment.py:337-345)
      goes through `_exact_token_window` (run_experiment.py:232-260), which does
      `decode` then `encode` with the TARGET's tokenizer, so the arms get
      in-range ids. Every approved campaign stage targets Llama-3.1-8B, whose
      tokenizer IS the pool's, so those stages are correct. The mismatch is
      confined to the gate's two Llama-2 controls.

  (b) a sampling call that can receive non-finite probabilities -- YES, two,
      and they are a latent device-side assert rather than a bad number:
        src/models/rasd_inference.py:322  torch.multinomial(probs, ...)
        src/models/rasd_inference.py:2039 torch.multinomial(resid, ...)
      both fed by `F.softmax` on target/draft logits (lines 317-322, 351-352,
      2035-2039). `torch.multinomial` aborts the CUDA context when the
      distribution is not finite. The gate does NOT reach these: its own
      generation is `do_sample=False` (greedy) at
      `scripts/mlsys_coherence_gate.py:340`. So this is not the 3c failure, but
      the sampling arms carry the same abort risk if a rope produces NaN logits.

  (c) can position ids exceed the rope cache -- NO, on either version.
      transformers 4.46.3 (the pod's pin, confirmed in the preflight) and
      4.47.1 both have a `LlamaRotaryEmbedding.forward` that computes
      `freqs = inv_freq @ position_ids` directly
      (modeling_llama.py:147-162) and never indexes a precomputed cos/sin
      table. `_dynamic_frequency_update` runs only `if "dynamic" in
      self.rope_type` (line 149) -- never for "yarn", "default" or "linear".
      There is no cache to overflow. (The field `max_seq_len_cached` exists but
      is read only by that never-taken branch.)

MEMORY: BOTH CANDIDATES FIT ON ONE GPU
  The gate loads one model at a time, `device_map={"": 0}`, bf16, unquantized.
    B_llama2_yarn8_32k_correct   Llama-2-7B    @32k   peak 13.75 GB
    N1_arm4_f2_construction     Llama-3.1-8B  @128k  peak 31.71 GB
  Both fit in 40 GB and in 80 GB, with SDPA as the attention backend.

THE FIX  (scripts/mlsys_coherence_gate.py)
  1. The prompt is tokenized by the CANDIDATE's tokenizer. `load_pg19_window`
     now takes the candidate tokenizer; when the pool's recorded tokenizer
     differs, the text at the same document and offset is re-tokenized with the
     candidate's, so the target is shown ids its own embedding can look up. When
     the two AGREE -- every Llama-3.1 candidate against this pool -- the ids are
     byte-for-byte what they were, so the controls already recorded for Llama-3.1
     stay comparable. There is a test for exactly that.
     The source length is found by BISECTION. Correcting one estimate at a time
     does not converge here: the map L <- L + span - f(L) has a contraction
     factor of -0.13 at Llama-2's 1.13 tokens per pool id, and it was measured
     oscillating 32767 -> 28403 -> 29001 -> 28928 with no exact hit in eight
     probes. An exact-length window matters because a longer one would measure

THE BLOCKER THE PROBE FOUND: EVERY STAGE WITH TWO ROWS WOULD HAVE DIED
The first probe run passed the canary (`status=ok tokens=4 rounds=1`) and then
the speculative row failed:

    REFUSING to write .../runexp_probe.csv for stage 'unnamed': the file
    already holds rows from ['probe_1x_canary_s42']

That is the filename-collision guard (added after the ARM4 driver pointed a
stage at an unrelated aggregate's filename). Two independent defects made it
refuse a stage's OWN file:

  1. It was called from the WORKER. The worker does not write the CSV at all --
     it writes a per-run `.tmp` that the parent reads and appends -- and
     `worker_args` never carried `--stage-id`, so `args.stage_id or "unnamed"`
     made every worker the stage "unnamed".
  2. Ownership was a NAME PATTERN (`stage_id.split("_")[0] in level_id`). That
     pattern cannot match this campaign: the stage is `engine_cap_smoke` and its
     levels are `CAPS_prefix64`.

So after the first row of any stage was written, every later row was refused,
the worker died, and with --abort-on-failure the stage failed. engine_cap_smoke
has 4 rows; every measurement stage has more. **The wandb error had been hiding
this: engine_cap_smoke died at init_wandb on row 1, before the guard could fire
on row 2.** Without this probe, the next 8xA100 launch would have died the same
way, one stage later, and cost the whole run.

THE FIX
  * The guard moved to the PARENT, the only process that writes the CSV and the
    only one that knows the stage and the level ids it will produce.
  * Ownership is now exact: the file is this stage's if every level id in it is
    one this stage plans to write. A previous attempt of the same stage passes,
    which is what makes a retry or --resume work; anything else is refused with
    the foreign level names quoted in the message. The canary's id is included
    because the canary appends to the same file first.
  * The worker no longer guards. 11 new tests in
    tests/test_run_experiment_output_guard.py: 11/11 FAIL against the pre-fix
    code, 11/11 pass after. The ARM4 protection is kept as a test
    (`pg19_short_target` writing into `pg19_multiseed.csv` is still refused).
  * The dry run's step 5 documented the old contract; it now tests both halves
    plus the regression (a stage coming back for its own second row).
