THE REAL FINDING: ARM4-f1 IS NOT AN ARM2 REPLICATION
--------------------------------------------------------------------------------
ARM4-f1 was intended as the native anchor that replicates Arm2 (both
Llama-3.1-8B + Llama-3.2-1B draft capped 4k). It does NOT: 0.2429 vs 0.8901.
The A6 provenance columns show three variables changed at once:

                    ARM2                 ARM4-f1
  context_length    131072               130944
  max_new_tokens    64 (unrecorded)      128
  ignore_eos        no                   YES
  prompt            OLD seed-INDEPENDENT  NEW A7 seed-dependent
                    (no sha256 column)   sha256 6419eab5/dafd7d6a/b49c2bd6

So "Arm2 replication at 2x rounds" is not a replication, and the 0.24 vs 0.89
gap cannot yet be attributed. The rope path is RULED OUT: with rope_factor=1
the loader returns hf_cfg unchanged, preserving Llama-3.1's native llama3
block (verified in src/models/rasd_inference.py and by the CPU pre-flight).

Leading hypothesis: max_new_tokens=128 with ignore_eos=True forces the model
past its natural stopping point into low-confidence territory where draft and
target disagree. The synthetic repeated-paragraph prompt is highly predictable
and likely saturates early; 64 forced tokens stay in-distribution, 128 do not.
n_rounds corroborates a real effect, not a bookkeeping bug: 63 rounds for 128
tokens = 2.03 tok/round (alpha~0.24), versus 14 rounds for 64 tokens = 4.57
tok/round (alpha~0.89).

NOT RESOLVED. Do NOT relaunch until this is diagnosed: the same confound would
invalidate every ARM4 rung, and a 256k/512k run (~$100+) built on it would be
wasted. Suggested next step is cheap: re-run ARM4-f1 with max_new_tokens=64 and
ignore_eos=False (one cell, ~$17) to isolate whether round count or the prompt
change drives the drop.
